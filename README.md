# Vortex Messenger 🌪️

> **Единое ТЗ и границы версии 1.0:** [docs/PROJECT_SPEC.md](docs/PROJECT_SPEC.md). Все задачи должны ссылаться на требования этого документа. Новые идеи по умолчанию относятся к версии после 1.0.


Веб-мессенджер на **Preact + Vite + Firebase Authentication/Firestore**. Проект на ранней стадии разработки и пока не предназначен для чувствительной переписки.

## Разработка

### Публикация на GitHub Pages

GitHub Pages должен публиковать **собранный Vite-сайт**, а не исходный `index.html`.
В настройках репозитория **Settings → Pages → Build and deployment → Source** выберите
**GitHub Actions**. Workflow `Deploy Vortex to GitHub Pages` собирает `dist` с базовым
путём `/Vortex/` и публикует его по адресу `https://doctorstrangesh.github.io/Vortex/`.
Если вместо приложения пустой экран и браузер запрашивает `/src/main.jsx` (404),
это означает, что Pages по-прежнему раздаёт исходники. Запуск workflow вручную
доступен в Actions после выбора GitHub Actions как источника публикации.

```bash
npm ci
npm run dev
npm test
npm run build
npm run test:rules
```

Для изолированного тестирования создайте `.env.staging.local` по `.env.example`, заполните
параметры отдельного Firebase-проекта и запускайте `npm run dev -- --mode staging`.
Неполная staging-конфигурация и смешение staging с ресурсами production блокируются.
Без `--mode staging` приложение по-прежнему использует существующий Firebase-проект.

Публичный Firebase API key в `src/services/firebase.js` не является серверным секретом: доступ к данным должны ограничивать серверные правила Firestore и Storage.

## Важные ограничения безопасности

- **Обычные сообщения не шифруются end-to-end.** Наличие `encryptionService.js` не означает, что он защищает обычную переписку. Нужен проверенный протокол, управление ключами и проверка устройств.
- **Двухфакторная аутентификация не реализована.** Небезопасная демонстрация удалена; вызовы сервиса теперь явно сообщают о недоступности MFA вместо выдачи ложного подтверждения.
- **Правила Firestore и Storage необходимо развернуть отдельно после staging-проверки.** Эмуляторные тесты положительных и отрицательных сценариев проходят, но они не заменяют проверку с реальными аккаунтами и настройками бакета.
- **Правила и эмуляторные тесты:** `firestore.rules`, `storage.rules`, `firebase.json`. Проверяются создание, чтение и удаление файлов, а также отзыв доступа к байтам файла после исключения из группы. В production эти правила ещё не применены.
- Пока флаг Storage выключен, небольшие вложения передаются в Firestore как data URL с лимитом 350 КБ.
- **Экспериментальный Storage:** при `VITE_USE_FIREBASE_STORAGE=true` новые вложения до 25 МБ загружаются в Storage; в сообщении сохраняется `storagePath`, а файл скачивается авторизованным `getBlob()` без постоянного URL-токена. Флаг по умолчанию выключен. Для браузерного скачивания необходимо настроить CORS; см. [проверку Storage в staging](docs/STORAGE_STAGING_CHECKLIST.md). Старые сообщения с токенами остаются в истории до отдельной миграции.
- Подписка чата получает последние 100 сообщений; более ранние страницы доступны по кнопке над историей (по 100 за раз). Ручная загрузка сохраняет положение прокрутки; автоматическая бесконечная прокрутка пока не включена.
- Новые личные чаты используют постоянный ID, рассчитанный из двух UID; ранее созданные чаты сохраняются. Нужны тесты с реальными Firestore rules, особенно для чтения ещё не созданного документа и конкурентного создания чата.
- Новые `@username` нормализуются и закрепляются вместе с профилем одной Firestore-транзакцией. Старые некорректные или смешанные по регистру username перед выпуском потребуют отдельной проверки/миграции.
- Если Firebase Authentication создал аккаунт, но профиль не сохранился, приложение показывает экран **«Завершить регистрацию»** вместо запуска чатов. Можно выбрать другой `@username` без повторной регистрации email; при временной ошибке чтения профиля доступен повторный запрос.
- Новое сообщение и превью чата записываются атомарно через Firestore batch; клиенту необходимы разрешения на обе записи. Защита авторства и порядка при конкурирующих отправках остаётся серверной задачей.

## Дорожная карта

1. **P0 — Безопасность:** проверить реальные Firestore rules, разграничить доступ участников чатов, запретить подмену авторства/чужое редактирование, реализовать проверяемую MFA.
2. **P0 — Надёжность:** стабильные ID личных чатов, атомарная отправка и превью, базовая пагинация (готова), офлайн-синхронизация.
3. **P1 — Медиа:** Firebase Storage, превью, ограничение размера и стоимости хранения.
4. **P1 — Приватность:** модель угроз, независимый аудит E2EE, управление ключами устройств.
5. **P1 — Продукт:** удобные группы и каналы, поиск, адаптивный интерфейс, уведомления, доступность.
6. **Постоянно:** unit/integration/e2e-тесты, Firebase Emulator, CI, мониторинг и план восстановления.

Никогда не публикуйте service-account JSON или другие серверные секреты в клиенте.

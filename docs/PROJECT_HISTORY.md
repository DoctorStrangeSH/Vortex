### 13.14. Запрет устаревших self-destruct metadata — 20.11.2026

Самоуничтожающиеся сообщения исключены из Vortex 1.0 (раздел 4.3), а UI и сервис создания этой функции удалены ранее. Аудит выявил оставшиеся legacy-поля selfDestruct и destructAt в Firestore Rules и отображение старого таймера в MessageBubble.

Изменения в отдельной ветке:
- Новые сообщения не могут создавать поля selfDestruct или destructAt.
- Автор сообщения больше не может добавлять или изменять эти поля при редактировании.

### 13.18. Безопасная очистка orphaned Storage attachments — 20.11.2026

После аудита 13.17 подтверждено, что удаление Firestore message document не удаляло связанный Firebase Storage object. Кроме того, прежнее Storage Rule разрешало владельцу удалять файл, пока сообщение ещё существовало, и запрещало очистку после выхода из чата.

**Реализация в ветке PR #73:**
- Storage object ID совпадает с Firestore message ID; это позволяет проверить ссылку на вложение по пути `chats/{chatId}/messages/{fileId}`.
- Storage Rules разрешают удаление только авторизованному владельцу пути и только если соответствующий Firestore message document уже отсутствует.
- Удаление больше не требует оставаться участником чата, поэтому автор может очистить orphan после выхода.
- Пока message document существует, удаление файла запрещено: участник не может намеренно сломать ещё действующее вложение.
- После успешной Firestore transaction в `messageService.deleteMessage` путь Storage object записывается в локальную durable cleanup queue; затем выполняется попытка удалить объект.
- Ошибка сети/Storage оставляет путь в очереди. Повтор выполняется при открытии чата и при событии `online`; уже отсутствующий объект считается очищенным.
- Повреждённая очередь сначала резервируется и блокирует автоматическую перезапись; недопустимые Storage paths отклоняются.

**Ограничения:**
- Очередь локальна для браузерного профиля и не синхронизируется между устройствами. Очистка данных сайта/профиля может удалить ожидающие cleanup tasks.
- Если localStorage недоступен или заполнен, немедленная очистка может не получить durable retry; это не должно приводить к удалению живого объекта.
- Это best-effort cleanup в клиенте, а не серверная гарантия. Cloud Functions, Blaze и изменение тарифа не используются.
- Firebase Storage остаётся opt-in; production Rules не публиковались.

**Проверки в PR #73:**

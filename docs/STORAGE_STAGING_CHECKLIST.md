# Проверка Firebase Storage перед включением в Vortex

Статус: **не выполнена в реальном staging**. Эмуляторные тесты не заменяют браузерную проверку.
Пока тест не пройден, `VITE_USE_FIREBASE_STORAGE` должен оставаться выключенным в production.

## 1. Окружение и CORS

1. Используйте отдельный тестовый Firebase-проект и тестовых пользователей, без реальных переписок.
2. Скопируйте `.env.example` в `.env.staging.local` и заполните **все** `VITE_FIREBASE_*`
   из отдельного Firebase-проекта. `VITE_APP_ENV=staging` обязателен: приложение отклонит
   неполный конфиг или случайное совпадение project ID, auth domain либо storage bucket с production.
   Запускайте `npm run dev -- --mode staging` (либо `npm run build -- --mode staging`).
   Обычный `npm run dev` продолжит использовать текущий production-конфиг.
3. Скопируйте `config/storage.cors.example.json` и подставьте **точные origins** тестового приложения
   (протокол + хост + порт; без пути). Пример разрешает только localhost и **не включает** production-домен.
4. Сначала сохраните текущую CORS-конфигурацию тестового бакета:
   ```bash
   gcloud storage buckets describe gs://STAGING_BUCKET --format="default(cors_config)"
   ```
5. После проверки имени бакета и origins примените конфигурацию только к тестовому бакету:
   ```bash
   gcloud storage buckets update gs://STAGING_BUCKET --cors-file=path/to/staging-cors.json
   ```
6. Убедитесь, что CORS разрешает `GET` для origin браузера. CORS **не заменяет** Firebase Storage Rules
   и не является проверкой членства в чате.

Официальная документация:
- https://firebase.google.com/docs/storage/web/download-files#cors_configuration
- https://cloud.google.com/storage/docs/using-cors

## 2. Браузерная матрица

В сборке staging включите `VITE_USE_FIREBASE_STORAGE=true` только после публикации
проверенных staging-правил и CORS. Откройте приложение в двух независимых профилях браузера.

| Шаг | Аккаунт А | Аккаунт Б | Ожидание |
| --- | --- | --- | --- |
| 1 | Создаёт тестовый чат с Б | Открывает чат | Оба видят чат |
| 2 | Отправляет PNG и файл | Обновляет страницу | Б скачивает содержимое без токена в Firestore |
| 3 | Открывает галерею | Открывает галерею | Изображения видны; консоль без CORS ошибок |
| 4 | Отправляет видео/аудио | Воспроизводит | Работает загрузка из `blob:` URL |
| 5 | Исключает Б из тестовой группы | Пытается повторно загрузить файл после перезагрузки | Отказ Firebase Storage Rules |
| 6 | Удаляет собственный тестовый файл | Пытается открыть его | Файл недоступен |

Проверьте DevTools → Network: `getBlob()` получает файл с текущей авторизацией.
В документе `chats/{chatId}/messages/{messageId}` должны быть `storagePath` и пустой
`fileData`, а не `https://...token=...`. Не публикуйте ID-токены и скриншоты с личными данными.

## 3. Критерии готовности и откат

- [ ] Проверены staging-проект, бакет и правила для двух аккаунтов.
- [ ] CORS разрешает реальные origins, запросы `GET` работают.
- [ ] Новые файлы не создают постоянных download URL.
- [ ] Неверный участник и исключённый участник получают отказ.
- [ ] Показаны ошибки, а не зависшее пустое вложение.
- [ ] Существующие вложения по-прежнему видны.
- [ ] Проверены скорость загрузки, объём памяти и стоимость больших медиа.

При сбое **сначала выключите флаг** `VITE_USE_FIREBASE_STORAGE` в staging и повторите деплой.
Не удаляйте Storage-объекты и не меняйте production-правила автоматически.

## 4. Наследие ссылок с токенами

Ранее созданные `getDownloadURL()` могут оставаться действительными независимо от членства
в чате. Новые сообщения больше не создают такие ссылки, но это **не отзывает старые токены**.
Отдельная миграция должна определить затронутые сообщения, перенести доступ на `storagePath`,
проверить успешное чтение, затем осторожно отозвать старые токены через администраторскую операцию
с резервной копией и журналом изменений. Не запускайте массовое удаление или замену без инвентаризации.

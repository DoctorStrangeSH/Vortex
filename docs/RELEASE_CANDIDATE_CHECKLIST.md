## B.1. Порядок выполнения первой двухаккаунтной сессии (RC-P01–RC-P06)

**Подготовка:** два добровольных участника (A и B), два независимых профиля браузера или устройства. Открыть [Production Vortex](https://doctorstrangesh.github.io/Vortex/) в каждом профиле. Использовать только новый временный тестовый диалог, нейтральные сообщения «RC-A-01» и «RC-B-01», не вводить рабочие/личные сведения. Записать дату, браузеры и ширину экрана. Не очищать данные сайта, пока есть недоставленные сообщения.

| Шаг | Проверка | Минимальный наблюдаемый критерий |
| --- | --- | --- |

## B.2. Порядок offline/reconnect-сессии (RC-P07–RC-P10)

Эта инструкция уточняет матрицу B и не меняет статусы до фактического наблюдения. Проводить **после** успешной базовой сессии RC-P01–P06, в том же временном тестовом чате.

**Подготовка:** сохранить список уже доставленных тестовых сообщений; убедиться, что очередь пуста и оба аккаунта онлайн. Использовать только один короткий маркер на сценарий: `RC-OFFLINE-07`, `RC-REOPEN-08`, `RC-TAB-09A`, `RC-TAB-09B`. Для отключения сети использовать DevTools → Network → Offline только в тестовом профиле A. После каждого сценария вернуть Online и дождаться подтверждения доставки до следующего шага.

| Шаг | Проверка | Безопасная процедура и критерий |
| --- | --- | --- |
| 1 | RC-P07 | Перевести A в Offline, отправить одно `RC-OFFLINE-07`, вернуть Online. B должен получить его ровно один раз; A должен увидеть подтверждённое состояние отправки |
| 2 | RC-P08 | Снова Offline, отправить одно `RC-REOPEN-08`, обновить только вкладку A, пока сеть отключена, затем вернуть Online. Сообщение должно сохраниться и прийти B ровно один раз |
| 3 | RC-P09 | Открыть две вкладки A одного профиля. При Offline отправить из первой `RC-TAB-09A`, из второй `RC-TAB-09B`; вернуть Online. B получает оба сообщения ровно по одному разу, порядок и автор корректны |
| 4 | RC-P10 | Только после полного опустошения очереди A выйти из аккаунта и войти аккаунтом B в том же профиле. У B не должны отображаться личные чаты A; не должно быть отправки сообщений от имени B из сессии A |

**Стоп-условия:** если сообщение не доставилось, появилось больше одного экземпляра, очередь показывает pending/failed либо состояние непонятно — прекратить следующий шаг, оставить профиль и site data нетронутыми, записать время/наблюдение. Не очищать localStorage, IndexedDB, cookies, кэш, не удалять чат и не повторять отправку «для проверки». Сначала сохранить диагностические сведения без токенов и личного содержимого.

**Граница P10:** Production smoke подтверждает только видимую изоляцию сессий/списка чатов после чистого выхода. Проверка, что недоставленная очередь A не может быть отправлена от имени B, относится к RC-S04/контролируемому staging или Emulator; специально оставлять pending-сообщения перед выходом из Production запрещено.

**Запись:** обновить статусы RC-P07–P10 только после наблюдения; указать браузер, устройство, вкладки и результат доставки. PASS одного сценария не закрывает остальные.

### C.2. Group / channel roles and access revocation (RC-S07) — staging only

Использовать два владельческих/административных и два обычных тестовых аккаунта, отдельную тестовую группу и канал. Не использовать реальные чаты или сотрудников.

1. Создать группу A с владельцем A, администратором B и участниками C/D. Проверить, что только владелец управляет списком admins; delegated admin не может назначить/снять администратора или удалить владельца.
2. Проверить, что администратор может удалить обычного участника, но не владельца и не другого администратора; участник может выйти только сам.
3. После удаления C проверить прямыми запросами, что C теряет чтение документа группы и старых сообщений, не может читать историю, отправлять/редактировать сообщения или менять участников. B и оставшиеся участники сохраняют доступ.
4. Создать канал с владельцем A и подписчиками B/C. Подписчик не может публиковать, менять ownerId/admins/subscriberCount, удалять другого подписчика или менять только один из participants/subscribers.
5. Проверить самостоятельную отписку B: participants, subscribers и subscriberCount меняются атомарно. После отписки B теряет чтение канала и сообщений и не может публиковать; A сохраняет доступ и публикацию.
6. Повторить негативные операции прямыми Firestore SDK/API вызовами из тестового клиента, а не только через UI; сохранить только обезличенные результаты.

**PASS:** все положительные и отрицательные сценарии воспроизводимы на staging, после удаления/отписки доступ отзывается немедленно, счётчик соответствует subscribers.size(), владелец остаётся защищён. При любом несоответствии — FAIL/BLOCKED; не ослаблять Rules для обхода.

Если отдельного staging нет, эти пункты остаются **BLOCKED**, а не автоматически закрываются успешным Production smoke или Emulator CI.

### C.3. Storage attachment lifecycle (RC-S08) — staging only

Подробная инструкция и браузерная матрица: [docs/STORAGE_STAGING_CHECKLIST.md](STORAGE_STAGING_CHECKLIST.md). Использовать только отдельный staging Firebase project/bucket и два временных тестовых аккаунта. Не включать Storage в Production и не менять Production CORS/Rules.

1. Проверить точные staging project ID, bucket, опубликованные Storage/Firestore Rules, CORS origins и backup/rollback перед тестом.
2. Отправить PNG и обычный файл из A в B; подтвердить, что Firestore хранит `storagePath` и пустой `fileData`, а не постоянный download token URL. B должен получить байты после reload.
3. Проверить отказ пустой загрузки, неверного MIME, запрещённых активных типов, неверного владельца пути, неучастника, повторной загрузки поверх существующего объекта и превышения согласованного лимита.
4. Удаление сообщения и удаление объекта проверить раздельно: живое сообщение не должно остаться без вложения; orphan cleanup доступен только владельцу объекта, в том числе после выхода из чата.
5. После исключения B из группы повторить metadata/read/download из старой вкладки и после reload — доступ должен быть отклонён. Оставшийся участник сохраняет чтение.
6. Проверить реальные браузерные CORS GET-запросы, ошибки сети/quota/permission-denied, повторную попытку, отсутствие зависшего индикатора и отсутствие утечки токенов в Firestore/логи.
7. Составить инвентаризацию legacy download URLs без вывода самих токенов; не отзывать и не переписывать их массово. Любая миграция — отдельный согласованный план с резервной копией и rollback.

**PASS:** все позитивные/негативные операции воспроизводимы на staging в двух независимых профилях, CORS работает только для согласованных origins, исключённый пользователь теряет доступ, удаление не ломает живые сообщения, legacy URLs инвентаризированы без destructive изменений. При любом сбое — FAIL/BLOCKED и откат только staging-флага.

### C.4. Attachment failure recovery (RC-S09) — Emulator / staging

Использовать отдельный staging/Emulator и временные тестовые аккаунты. Не создавать искусственные quota incidents в Production и не удалять пользовательские данные.

1. **Permission denied:** отозвать доступ тестовому аккаунту; убедиться, что интерфейс сообщает об отсутствии доступа и не предлагает бесконечный retry.
2. **Invalid file:** выбрать файл выше лимита и файл с запрещённым/некорректным MIME; интерфейс показывает причину и не предлагает бессмысленный повтор. Повторные попытки доступны только для исправленного файла.
3. **Quota exceeded:** смоделировать код ошибки на уровне сервиса/теста; убедиться, что показано отдельное сообщение о квоте и автоматическая повторная загрузка отключена.
4. **Network interruption:** оборвать соединение до завершения Storage upload; файл остаётся в состоянии ошибки, повтор доступен только после восстановления связи.
5. **Unknown Firestore commit:** оборвать подтверждение после возможной записи сообщения; приложение не удаляет потенциально используемый Storage object и не предлагает слепую повторную отправку.
6. **Confirmed absent commit:** если lookup однозначно подтвердил отсутствие сообщения, допускается одна повторная запись с тем же message ID; бесконечный цикл запрещён.
7. **Partial batch:** при ошибке второго/третьего файла ранее отправленные не дублируются; пользователь видит число успешных отправок и повторяет только оставшиеся файлы.
8. **Cleanup failure:** при временной ошибке удаления путь остаётся в локальной очереди; object-not-found считается уже очищенным; повреждённая очередь не перезаписывается без восстановления.
9. **Recovery:** после возврата сети повторить допустимые операции; сверить Firestore message IDs и Storage object paths, убедиться в отсутствии дублей, orphan leaks и потерянных сообщений.

**Дополнительная проверка retry allowlist:** смоделировать известные временные коды (`storage/network-request-failed`, `storage/retry-limit-exceeded`, `unavailable`, `deadline-exceeded`, `aborted`, `attachment/read-failed`) — повтор разрешён ограниченно; для неизвестного кода — повтор отключён и показана инструкция проверить файл/соединение. Для uncertain commit повтор запрещён до проверки истории чата.

**PASS:** ошибки классифицированы правильно, quota/permission/invalid/unknown не запускают автоматический retry, только allowlist временных ошибок повторяется ограниченно, uncertain commit не создаёт дубль и не удаляет потенциально привязанный файл, очередь очистки сохраняет данные до подтверждённого результата. Все сценарии должны быть зафиксированы на staging/Emulator.

## C.1. Legacy registration / profile recovery (RC-S03) — staging only

**Запрещено проводить recovery-эксперименты на Production.** Нужен отдельный Firebase staging project с тестовыми Auth/Firestore данными, Emulator Suite либо одноразовые тестовые учётные записи. Не импортировать реальные пароли, токены, email коллег или содержимое рабочих профилей. До теста сохранить экспорт/backup staging-данных и записать project ID, чтобы не перепутать окружения.

1. **Чистая регистрация:** создать тестовый аккаунт A с новым username; проверить, что Auth UID, private profile, public profile и username claim связаны корректно.
2. **Конфликт username:** попытаться зарегистрировать B с тем же нормализованным username; ожидается отказ без присвоения claim A, без перезаписи профиля A и без создания второго Auth UID из-за повторного submit.
3. **Повторный вход:** выйти и войти A; приложение не должно повторно запрашивать имя/username и не должно создавать новый профиль.
4. **Частичная регистрация:** в staging/Emulator смоделировать Auth account без завершённого profile/claim; войти тем же UID и продолжить через «Завершить регистрацию», не создавая второй Auth account.
5. **Существующий claim того же UID:** восстановление допускается только при точном совпадении UID и нормализованного username; операция должна быть идемпотентной.
6. **Чужой/повреждённый claim:** конфликтующий UID, несовпадающее имя и malformed claim должны приводить к безопасному отказу; существующая запись не перезаписывается, публичный профиль не раскрывает приватные поля.
7. **Публичная/приватная граница:** публичный поиск показывает только разрешённые поля; email и приватные данные остаются недоступны публичному клиенту.
8. **Rollback:** восстановить staging snapshot и повторить контрольную проверку; убедиться, что восстановление не затронуло другие тестовые UID.

**Критерий PASS:** все сценарии 1–8 имеют зафиксированные результаты и воспроизводимы; в логах нет секретов; Security Rules не ослаблялись. Любой конфликт, требующий ручного перезаписывания claim, — FAIL/BLOCKED и отдельный дефект, а не повод обходить защиту.

**Важно:** успешный Emulator run подтверждает тесты правил/логики, но не реальное состояние legacy Production документов. RC-S03 остаётся NOT TESTED до staging-проверки с отдельными данными и согласованного отчёта. Никаких production migrations или bulk repairs в рамках этой приёмки.

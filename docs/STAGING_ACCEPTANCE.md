# Vortex 1.0 — staging acceptance runbook

**Статус:** подготовлено; staging-приёмка не выполнена.  
**Дата:** 23.11.2026  
**Источник требований:** docs/PROJECT_SPEC.md, разделы 5–8 и release gates в ROADMAP.md.

Этот документ фиксирует только проверку уже согласованного scope Vortex 1.0. Он не добавляет продуктовых функций.

## 1. Безопасная подготовка окружения

- [ ] Владелец создаёт отдельный Firebase-проект для staging на Spark.
- [ ] Проверить, что Project ID, Auth domain и Storage bucket staging отличаются от production.
- [ ] Не подключать billing / Blaze.
- [ ] Не включать Storage до отдельного подтверждения, что его использование необходимо и соответствует бесплатному тарифу.
- [ ] Создать два тестовых аккаунта A и B с отдельными адресами; не использовать личные/production аккаунты.
- [ ] Подготовить два независимых браузерных профиля или два браузера.
- [ ] Сохранить текущие staging Rules перед публикацией; публиковать только rules из проверяемого commit.
- [ ] Проверить выбранный Firebase project перед каждой командой deploy. Запрещено выполнять staging deploy с production project ID.
- [ ] Не помещать .env, service-account keys, токены и пароли в Git.

Staging-конфигурация приложения передаётся через все шесть параметров VITE_FIREBASE_* и VITE_APP_ENV=staging. Режим staging должен завершаться ошибкой при неполной конфигурации или совпадении production-ресурсов. См. src/services/firebaseConfig.js.

## 3. Протокол дефектов

Для каждого FAIL записать:
- ID проверки;
- commit SHA и URL staging build;
- браузер / ОС / viewport;
- аккаунт и роль (A, B или outsider; не записывать пароли и токены);
- точные шаги воспроизведения;
- ожидаемое и фактическое поведение;
- скриншот или безопасный журнал без персональных данных.

P0/P1 дефекты блокируют RC. После исправления повторить исходный сценарий и соседние регрессии.

## 4. Критерии выхода

Staging gate считается пройденным только если:
1. Все применимые проверки таблицы имеют PASS.
2. Ни один P0/P1 дефект не остаётся открытым.
3. Проверены два независимых аккаунта и отдельный outsider.
4. Подтверждены offline recovery, отсутствие дублей и отзыв доступа.
5. Ручная мобильная, keyboard и screen-reader приёмка зафиксирована.
6. Зафиксированы commit SHA, staging project ID (не секрет), дата, браузеры и результаты.
7. Production не менялся в ходе staging-приёмки.

После этого можно собирать RC checklist. Этот runbook сам по себе не подтверждает готовность staging, Production Rules или выпуска 1.0.

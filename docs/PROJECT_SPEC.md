# Vortex — Product & Technical Specification

**Версия:** 1.0.0 · **Дата:** 20.11.2026 · **Статус:** базовая версия для утверждения владельцем  
**Целевой релиз:** Vortex Web Messenger 1.0 · **Основной язык UI:** русский

## 1. Назначение и приоритет документа

Этот документ — единый источник требований для владельца, разработчиков, дизайнеров, тестировщиков и будущих участников Vortex. Его цель — закончить согласованный продукт, а не бесконечно расширять его.

Каждая задача, PR и проверка релиза должны ссылаться на идентификатор требования или раздел этого документа. Наличие файла, компонента, сервиса, ветки или незавершённого PR не доказывает, что функция готова.

При конфликте:
1. Ограничения бюджета и безопасности из разделов 3 и 8 имеют высший приоритет.
2. Границы версии 1.0 из раздела 4 важнее старых roadmap и обсуждений.
3. Этот документ определяет продуктовый scope.
4. Профильные документы определяют технические детали только внутри этого scope.

## 2. Продукт

### 2.1. Видение

Vortex — адаптивный веб-мессенджер для личного общения и небольших сообществ. Главная ценность версии 1.0 — простая, быстрая и надёжная переписка, одинаково понятная на компьютере и небольшом экране.

Vortex 1.0 не пытается повторить весь Telegram. Это законченный базовый продукт, который можно безопасно тестировать, выпускать и поддерживать.

### 2.2. Принципы

1. Надёжность переписки важнее количества функций.
2. Безопасность важнее удобства, если они конфликтуют.
3. Интерфейс должен быть понятен без инструкции.
4. Сетевые ошибки не должны приводить к тихой потере сообщений.
5. Функция не объявляется готовой, защищённой или зашифрованной без проверяемых доказательств.
6. Новые идеи не расширяют текущий релиз автоматически.

### 2.3. Платформа

- Браузерное приложение для настольных ПК, планшетов и телефонов.
- Целевые браузеры: актуальные стабильные Chrome, Edge, Firefox и Safari — после проверки совместимости.
- Нативные приложения iOS/Android в 1.0 не входят.
- Текущая публикация — GitHub Pages через GitHub Actions.

## 3. Непереговорные ограничения

### 3.1. Бюджет

**Владелец зафиксировал Firebase Spark (бесплатный тариф).**

До отдельного явного разрешения запрещено:
- переводить Firebase на Blaze/платный план;
- подключать платные API, модели ИИ, хостинг, базы и сторонние сервисы;
- включать платные фоновые функции, триггеры, серверные обработчики или инфраструктуру звонков;
- создавать TURN/SFU-серверы;
- запускать тесты, миграции и массовые операции с риском расходов или исчерпания квот.

Любая обязательная зависимость Vortex 1.0 должна работать в подтверждённых бесплатных возможностях текущего стека. Если безопасная реализация требует платного тарифа, функция переносится за пределы 1.0. Нельзя молча менять тариф или архитектуру.

Firebase Storage остаётся выключенным, пока не подтверждены доступность операций на текущем тарифе, правила, CORS и upload/read/revocation в отдельном staging-проекте. Текущий документированный fallback — ограниченные вложения в Firestore до 350 КБ.

### 3.2. Технические ограничения

- Firebase client API key не является секретом; доступ защищают Security Rules.
- Service-account JSON, пароли, приватные ключи и административные токены запрещены в клиентском bundle и Git.
- Production не используется для разработки и тестирования.
- Firestore/Storage Rules сначала проверяются локально, затем в staging.
- Нельзя ослаблять правила ради прохождения одного теста.
- Нельзя считать Emulator доказательством совместимости production.
- Если функция не реализуема безопасно в Spark, она не блокирует релиз: её исключают из 1.0.

## 4. Границы версии 1.0

### 4.1. P0 — обязательно для выпуска

1. Регистрация, вход, выход и восстановление доступа.
2. Имя и уникальный @username вводятся при регистрации в одном процессе.
3. Разделение приватного профиля и публичной карточки.
4. Личные чаты между двумя пользователями.
5. Отправка/получение текстовых сообщений в реальном времени.
6. История сообщений с постраничной загрузкой.
7. Надёжная отправка при временном offline без потери и дублирования.
8. Состояния прочтения только в пределах реально проверенной модели.
9. Защищённые правила доступа к профилям, чатам и сообщениям.
10. Адаптивность и прокрутка на небольших экранах.
11. Понятные загрузка, пустые состояния, ошибки и восстановление после сбоев.
12. Автоматические тесты, проверка правил и воспроизводимая сборка.

### 4.2. P1 — входит в релиз, только если выполнены те же критерии качества

1. Групповые чаты: создание, список участников, владелец, администраторы, добавление/удаление участника, самостоятельный выход.
2. Каналы: создание, подписка/отписка, публикация только владельцем/администраторами.
3. Базовые вложения в пределах подтверждённых бесплатных ограничений.
4. Реакции и закрепление сообщений — при корректных UI и Security Rules.
5. Базовые уведомления внутри открытого приложения.
6. Светлая/тёмная тема и утверждённый стиль Obsidian Iris.
7. Поиск пользователей по уникальному @username.
8. Восстановление профиля после частично завершившейся регистрации.

P1 не разрешает выпускать небезопасную или нестабильную реализацию. Если критерии не пройдены, функция отключается или переносится; качество P0 не снижается ради неё.

### 4.3. Не входит в 1.0 (POST-1.0)

- E2EE обычных чатов, секретные чаты и самоуничтожающиеся сообщения.
- Полноценная 2FA, пока она недоступна в утверждённой бесплатной конфигурации.
- Голосовые/видеозвонки, групповые звонки, TURN/SFU.
- Полноценная фоновая push-доставка с сервера.

Для POST-1.0 прототипы `encryptionService`, `secretChatService` и `pushService` должны оставаться fail-closed: криптографические операции и секретные чаты отклоняются, push не запрашивает разрешение браузера и не имитирует серверную доставку. Наличие локального Notification API не считается push-доставкой.
- ИИ-ассистент и платные AI API.
- Большие файлы, безлимитное медиа и платное хранилище.
- Каталог/рекомендации каналов и сложная модерация.
- Сложные роли, пространства, команды, боты и автоматизации.
- Нативные приложения.
- Синхронизация криптографических ключей между устройствами.
- Аналитика, реклама, монетизация и социальные/игровые функции сверх согласованного сценария.

Существующие прототипы отложенных функций не считаются готовыми. Они должны быть скрыты, отключены или честно помечены как недоступные. Нельзя показывать ложный успех. Наличие encryptionService не означает E2EE; наличие twoFactorService не означает MFA; pushService не означает серверную push-доставку.

## 5. Функциональные требования

### 5.1. AUTH — регистрация и вход

- **AUTH-01:** регистрация email/пароль.
- **AUTH-02:** имя и @username вводятся при регистрации; после успешного сохранения не запрашиваются повторно.
- **AUTH-03:** username нормализуется и атомарно закрепляется за UID.
- **AUTH-04:** если Firebase Auth создал аккаунт, а профиль не сохранился, показывается «Завершить регистрацию»; второй аккаунт создавать не нужно.
- **AUTH-05:** черновик регистрации может временно хранить имя и username в текущей сессии; пароль и токены не сохраняются в нём.
- **AUTH-06:** вход, выход и восстановление пароля.
- **AUTH-07:** ошибки локализованы и не раскрывают приватные данные других пользователей.

**Приёмка:** два аккаунта регистрируются; конфликт username не создаёт дубликатов; повторный вход не требует повторной регистрации; частично созданный аккаунт восстанавливается.

### 5.2. USER — профиль и поиск

- **USER-01:** приватные данные отделены от публичной карточки.
- **USER-02:** публичная карточка содержит только UID, имя, username, необязательное описание и явно публичные поля.
- **USER-03:** email и приватные поля не доступны через публичный поиск.
- **USER-04:** пользователь изменяет только разрешённые поля собственного профиля.
- **USER-05:** нельзя занять, изменить или удалить чужой username claim.
- **USER-06:** поиск первой версии — по @username; email-поиск выключен.

**Приёмка:** два аккаунта находят публичные карточки друг друга, но не читают приватные документы и не меняют чужой профиль/username.

### 5.3. CHAT / MSG — личная переписка

- **CHAT-01:** начать личный чат с найденным пользователем.
- **CHAT-02:** стабильный ID пары пользователей предотвращает дубли при конкурентном создании.
- **CHAT-03:** только участники читают чат, сообщения и связанные данные.
- **MSG-01:** отправка и получение текста в реальном времени.
- **MSG-02:** sender UID определяется текущей Auth-сессией; нельзя писать от чужого UID.
- **MSG-03:** сообщение и preview не расходятся при штатной отправке; атомарная запись используется там, где её разрешают правила.
- **MSG-04:** повторная отправка использует стабильный ID и не создаёт дубль.
- **MSG-05:** история загружается страницами по 100; положение прокрутки сохраняется при открытии старой истории.
- **MSG-06:** список чатов сортируется по последней активности.
- **MSG-07:** редактировать/удалять можно только собственные сообщения, если действие доступно в UI.
- **MSG-08:** реакции и закрепление разрешены только при проверке участника и конкретного изменяемого поля.
- **MSG-09:** senderId, createdAt, chatId и другие неизменяемые поля нельзя подменить после создания.

**Приёмка:** A и B обмениваются сообщениями в двух браузерных профилях; realtime работает без ручной перезагрузки; посторонний не читает чат; чужое авторство и редактирование отклоняются.

### 5.4. SYNC — офлайн и восстановление

- **SYNC-01:** при потере сети виден статус ожидания отправки.
- **SYNC-02:** очередь хранит сообщение до подтверждения удалённой записи.
- **SYNC-03:** повтор использует прежний ID и не создаёт дубль.
- **SYNC-04:** очередь привязана к UID; после смены аккаунта чужое сообщение не отправляется.
- **SYNC-05:** восстановление сети, фокус вкладки и возвращение видимости возобновляют очередь.
- **SYNC-06:** ошибка локального хранилища не очищает очередь бесшумно.

**Приёмка:** отключить сеть, отправить сообщения, обновить/закрыть вкладку, вернуть сеть; каждое сообщение доставляется ровно один раз от исходного аккаунта.

### 5.5. READ — прочтение и непрочитанные

- **READ-01:** сообщение помечается прочитанным, только если реально показано пользователю в активном чате.
- **READ-02:** нельзя помечать чужие сообщения прочитанными от имени другого UID.
- **READ-03:** состояние согласовано между сессиями одного пользователя в рамках проверенной модели.
- **READ-04:** нельзя обещать точные серверные unread counters до реализации доверенной записи, идемпотентности, обработки неупорядоченных событий и миграции.

**Приёмка:** два аккаунта/две сессии проверяют чтение, повторные события и обновление страницы; повторная доставка события не меняет итог второй раз.

### 5.6. GROUP — группы

- **GROUP-01:** группа имеет название, создателя/владельца, участников и администраторов.
- **GROUP-02:** создатель получает права владельца/администратора при создании.
- **GROUP-03:** администратор управляет участниками в рамках проверенной модели.
- **GROUP-04:** участник может выйти самостоятельно, если это не нарушает инварианты группы.
- **GROUP-05:** нельзя удалить владельца, оставить группу без администратора или самостоятельно выдать себе роль.
- **GROUP-06:** права проверяются Security Rules; UI не является границей безопасности.
- **GROUP-07:** удаление группы не должно оставлять бесконтрольные подколлекции. До проверенной каскадной очистки прямое удаление группы запрещено.
- **GROUP-08:** журнал действий показывается только при проверенной схеме и правах. Нельзя выдумывать историю старых групп.

**Приёмка:** владелец, администратор, участник и посторонний проходят позитивные/негативные тесты; прямой запрос не обходит роли.

### 5.7. CHANNEL — каналы

- **CHANNEL-01:** создатель становится владельцем/администратором.
- **CHANNEL-02:** доступный пользователю канал поддерживает подписку и отписку.
- **CHANNEL-03:** subscribers, participants и subscriberCount меняются согласованно; повторная подписка не увеличивает счётчик.
- **CHANNEL-04:** публикуют только владелец/администраторы.
- **CHANNEL-05:** подписчик не может выдать себя за администратора или менять чужие подписки.
- **CHANNEL-06:** каталог рекомендаций и сложная модерация не входят в 1.0.

**Приёмка:** два пользователя подписываются/отписываются; счётчик корректен; подписчик не публикует; посторонний не читает закрытый канал.

### 5.8. MEDIA — вложения

- **MEDIA-01:** разрешены только типы и размеры, реально поддержанные бесплатным окружением.
- **MEDIA-02:** пока Storage не прошёл staging, используется только ограниченный текущий путь; задокументированный лимит data URL — 350 КБ.
- **MEDIA-03:** проверяются размер, MIME/type и принадлежность файла чату.
- **MEDIA-04:** если Storage включён, исключённый участник теряет доступ по правилам.
- **MEDIA-05:** постоянные download URL с токенами не заменяют авторизацию.
- **MEDIA-06:** большие файлы и безлимитное хранение вне 1.0.

**Приёмка:** разрешённый участник читает допустимый файл; посторонний/исключённый получает отказ; UI показывает ошибку, а не вечную загрузку.

### 5.9. NOTIFY — уведомления

- **NOTIFY-01:** базовые уведомления внутри открытого приложения.
- **NOTIFY-02:** повторный snapshot/event не создаёт дубликат уведомления.
- **NOTIFY-03:** фоновая push-доставка с сервера не обещается и не включается без утверждённой бесплатной инфраструктуры.

### 5.10. UI — интерфейс

- **UI-01:** утверждённое направление — Obsidian Iris: аккуратная тёмная поверхность, выразительный фирменный акцент, ясная иерархия и умеренные эффекты.
- **UI-02:** единый знак Vortex в приложении, favicon и мобильной вкладке.
- **UI-03:** на узком экране доступны все экраны, меню, формы и диалоги; прокрутка не блокируется.
- **UI-04:** формы имеют состояния загрузки, ошибки, успеха и повтора.
- **UI-05:** основные действия доступны с клавиатуры, фокус видим, иконки-кнопки подписаны.
- **UI-06:** анимации не мешают чтению и взаимодействию.
- **UI-07:** UI первой версии на русском; сырые Firebase errors не показываются без объяснения.

**Приёмка:** проверить ширины 320, 360, 390, 768, 1024 и 1440 CSS px; основные действия доступны, длинные формы и диалоги прокручиваются.

## 6. Нефункциональные требования

### Надёжность
Нет тихо потерянных сообщений; повторная отправка идемпотентна; offline/online и ошибки восстанавливаются; после обновления страницы состояние очереди не теряется.

### Производительность
Не загружать всю историю; использовать страницы по 100; виртуализировать длинные списки; избегать повторных подписок/запросов; не загружать большие медиа автоматически.

### Безопасность и приватность
Принцип минимальных прав; проверка членства в Rules; приватные профили доступны владельцу; публичные профили не содержат email; авторство и неизменяемые поля проверяются; чтение/запись/удаление/Storage проверяются отдельно; позитивные и негативные тесты обязательны. Обычная переписка 1.0 не имеет E2EE.

### Доступность
Контраст, видимый фокус, клавиатурное управление, подписи кнопок, reduced motion; ошибки не обозначаются только цветом.

### Совместимость
Проверка целевых браузеров и мобильного viewport; неподдерживаемая возможность должна показывать ограничение, а не ломать приложение.

## 7. Архитектура и данные

### 7.1. Текущий стек

- UI: Preact.
- Сборка: Vite.
- Auth: Firebase Authentication.
- Realtime/data: Cloud Firestore.
- Файлы: Firebase Storage только после подтверждения тарифа и staging.
- Хостинг: GitHub Pages.
- Тесты: Node test runner, Playwright smoke, Firebase Emulator Suite, Vite build.
- Язык: JavaScript/JSX, ES modules.

Не добавлять новый framework/backend без доказанной необходимости и отдельного решения.

### 7.2. Основные сущности

| Путь | Назначение |
| --- | --- |
| users/{uid} | приватный профиль |
| publicProfiles/{uid} | публичная карточка |
| usernames/{username} | уникальный claim |
| chats/{chatId} | личный чат, группа или канал |
| chats/{chatId}/messages/{messageId} | сообщения |
| chats/{chatId}/typing/{uid} | состояние набора |
| users/{uid}/unreadChats/{chatId} | приватная unread-проекция, если включена |
| chats/{chatId}/membershipHistory/{eventId} | журнал членства, если включён |
| chats/{chatId}/media/{uid}/{fileId} | Storage-объекты, если включены |

Изменение схемы сопровождается описанием миграции, обратной совместимости и тестами.

### 7.3. Граница доверия

Клиент недоверенный. UID, роли, авторство, размеры файлов и ссылки, присланные клиентом, проверяются Security Rules или доверенной инфраструктурой, разрешённой тарифом.

Обязательная версия не должна зависеть от неразвёрнутых Cloud Functions. Если безопасная реализация требования невозможна в Spark, оно переносится из 1.0 до отдельного решения владельца.

### 7.4. Spark-совместимая модель групп (решение от 21.11.2026)

Для Vortex 1.0 оставляем текущую модель `main`: клиентские операции создания группы и изменения членства проходят через Firestore Security Rules. Rules проверяют UID текущей сессии, владельца, список администраторов, допустимый переход состава участников и инварианты выхода. Это покрыто Emulator Suite тестами, включая обычного участника, делегированного администратора и защиту владельца.

PR #32 с переводом клиента на callable Cloud Functions закрыт без merge: он основан на сильно устаревшей ветке, добавляет зависимость от неразвёрнутых функций и может потребовать Blaze. Это несовместимо с зафиксированным Firebase Spark и не требуется для GROUP-01—GROUP-07 при текущей проверенной модели Rules. Ветка сохранена для справки; код не публиковался и не развёртывался.

GROUP-08 (журнал действий) остаётся условным: в 1.0 не показываем журнал, если нет проверенной схемы и прав. Callable-backed membership history, baseline для старых групп и серверная запись событий отложены в POST-1.0 либо до отдельного решения владельца по инфраструктуре. Историю прошлых действий не выдумывать.

Не ослаблять Rules ради совместимости. Если будущая проверка обнаружит обход, исправлять его отдельным изменением Rules + Emulator tests. Production deploy, смена тарифа и Functions deploy запрещены без отдельного разрешения владельца.

## 8. Безопасность и миграции — релизные ворота

### SEC-01. Production Rules
Документация репозитория фиксирует расхождение опубликованных production rules и локальных rules. До релиза:
1. Зафиксировать текущие production rules и схему данных.
2. Создать отдельный staging Firebase project.
3. Применить candidate rules только в staging.
4. Проверить старые/новые аккаунты, регистрацию, восстановление профиля, личные чаты, группы и каналы.
5. Проверить два независимых аккаунта и отказ постороннего.
6. Подготовить rollback.
7. Только после этого владелец вручную решает вопрос production rollout.

### SEC-02. Storage
Storage выключен до положительного staging-теста upload/read/revocation, CORS и миграции старых токенизированных ссылок. Не удалять старые объекты/токены без инвентаризации и резервного плана.

### SEC-03. Существующие данные
Не считать старые username, чаты, сообщения и вложения совместимыми с новой схемой без проверки. Массовая миграция имеет dry-run, резервную копию, отчёт, критерий остановки и план восстановления. Историю членства нельзя выдумывать из текущего participants массива.

### SEC-04. E2EE и MFA
В 1.0 они не заявляются. Файлы encryptionService, secretChatService и twoFactorService не являются доказательством защиты. README и UI не должны обещать E2EE/MFA до реализации и независимой проверки.

## 11. Управление изменениями — защита от бесконечного расширения

### 11.1. Что разрешено без пересмотра scope
- исправление дефекта;
- закрытие уязвимости;
- надёжность существующей функции;
- тест, доказывающий готовность;
- доступность/адаптивность согласованного сценария;
- документация и обслуживание сборки.

### 11.2. Что требует решения владельца
- новая пользовательская функция;
- новая внешняя зависимость;
- новые расходы или смена тарифа;
- новая коллекция или миграция production;
- изменение заявленного уровня приватности;
- изменение утверждённого UX-потока;
- перенос post-1.0 функции в текущий релиз.

### 11.3. Формат запроса на изменение
Каждое предложение содержит:
1. Пользовательскую проблему.
2. Почему текущий scope её не решает.
3. Стоимость разработки и поддержки.
4. Влияние на безопасность, данные, тариф и сроки.
5. Какую задачу 1.0 оно заменяет или почему не задерживает релиз.
6. Решение владельца: принять в 1.0, перенести в backlog или отклонить.

По умолчанию новая идея получает статус **POST-1.0**. Ни разработчик, ни ИИ, ни ревьюер не добавляет функцию в 1.0 самостоятельно.

### 13.18. Безопасная очистка orphaned Storage attachments — 20.11.2026

После аудита 13.17 подтверждено, что удаление Firestore message document не удаляло связанный Firebase Storage object. Кроме того, прежнее Storage Rule разрешало владельцу удалять файл, пока сообщение ещё существовало, и запрещало очистку после выхода из чата.

- Storage Rules разрешают удаление только авторизованному владельцу пути и только если соответствующий Firestore message document уже отсутствует.
- Удаление больше не требует оставаться участником чата, поэтому автор может очистить orphan после выхода.
- Пока message document существует, удаление файла запрещено: участник не может намеренно сломать ещё действующее вложение.
- После успешной Firestore transaction в `messageService.deleteMessage` путь Storage object записывается в локальную durable cleanup queue; затем выполняется попытка удалить объект.

- Если localStorage недоступен или заполнен, немедленная очистка может не получить durable retry; это не должно приводить к удалению живого объекта.
